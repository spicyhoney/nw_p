# 創新方向脈絡

## 定位

暫定產品主題：

> 台語友善、會主動補問、可隨時轉真人的高齡生活管家

本文件記錄探索方向，不是完成清單、API contract 或已核准 backlog。後續必須一項一份 Feature Spec，且在 `competition-constraints.md` 人工確認前不得產生 Spec 或 implementation tasks。

原始輸入列出 1–7 項；本文件將第 1–6 項視為六項產品創新，第 7 項另列部署方向。這個分組仍需團隊確認。

## 六項產品創新

| # | 方向 | 命題對應 | 目前 baseline | 主要缺口與不可破壞條件 |
|---:|---|---|---|---|
| 1 | 台語／國語語音輸入，轉繁體中文確認及查詢；支援台語語音輸出 | 命題容許文字或語音描述；企業工作坊展示語音能力；高齡友善是延伸建議。 | 只有文字 Web／Agent；Agent README 僅描述概念接法。 | STT/TTS provider、台語腔調與品質未知；轉寫先回顯確認，地址／時間／PII／寫入不得直接採信；預設不留原音。 |
| 2 | 引導式多輪補問地址、時間、預算、緊急程度；多項任務各自保存狀態 | 命題建議彈性問答表單與依地區、時段、預算、緊急程度媒合；工作坊願景提到一次安排多項服務。 | 可查服務／地點／表單、跨輪追問部分欄位，Web 有單一 process-local session 與人工表單。 | 目前不能泛化 slot filling，也沒有多 task state；絕不預設臺北市，每項任務需獨立 ID、欄位、確認、取消與保存政策。 |
| 3 | 使用者可隨時要求轉接真人 | 官方 PDF 未把真人轉接列為必做；它是團隊為高齡信任、失敗復原與可及性提出的差異化設計。 | 無真人 channel、queue、客服 UI 或 SLA。 | 不得假裝已轉接；需決定 channel、營業時間、責任、摘要範圍、同意、逾時與緊急情境。 |
| 4 | 師傅登記台語及其他語言能力，媒合納入偏好 | 命題允許依服務商條件設計媒合，但語言能力是團隊延伸，不是官方要求。 | `matching_v1` 只看時段、評分、經驗、費用；服務商全為 synthetic。 | 語言能力須有來源／更新方式，區分「自述能力」與「驗證能力」；語言偏好不應不當排除或推測族群，政策需版本化及可解釋。 |
| 5 | 將既有照片服務判斷整合進多輪對話，不重新實作 | 官方表單資料支援照片題型；照片可降低修繕描述負擔。 | 已有安全上傳、HF VLM 建議、人工更正／確認與服務目錄重驗，並部分串入 Web 諮詢／案件。 | 應重用現有 storage、VLM 與確認 API，只調整對話／task orchestration；不得另建平行分析服務、直接診斷、直接派單或繞過同意。 |
| 6 | 探索高齡互動及點數機制 | 命題建議高齡友善；企業工作坊願景提到使用服務累積點數。 | 已有無障礙基線；沒有點數 domain、ledger 或政策。 | 高齡友善不只大字；點數不得按聊天次數，須先處理成癮、洗點、詐欺、誤導、隱私、撤銷及公平性。可選擇不做點數。 |

## AWS 部署方向（不是已完成創新）

團隊預計最終系統朝 AWS 部署，但官方目前明確要求的是簡報中的 AWS 雲端技術架構與可存取的 Live Demo 網址；提供資料沒有指定 Region、模型或特定 AWS 服務。Bedrock、AgentCore、RDS、S3、IAM、CloudWatch 與 hosting 皆是候選選型，尚無 adapter 或部署證據。

Spec 不得先假設：

- 一定使用 Bedrock 或哪個 foundation model。
- 一定使用 AgentCore Runtime／Gateway。
- Demo 一定部署於 AWS。
- 固定 Region、帳號、網路、IAM、預算或資料落地區域。

## 創新取捨準則

1. 先解決高齡使用者的真實障礙，再追求功能數量。
2. 優先展示「台語友善 + 可核對補問 + 真人出口」的一條可信閉環。
3. 每項創新要能對應使用者痛點、命題、資料、技術證據與 Demo 畫面。
4. 新模型或新服務不等於創新；必須說明為何比現有流程更安全、可用或可及。
5. 不為加分回溯性捏造 Kiro、AWS、模型或使用者測試紀錄。

## 仍需人類決定

- 是否確認以第 1–6 項作六項產品創新、AWS 作獨立部署方向。
- 主要 persona 是獨居高齡者、與家人同住高齡者、照顧者代理，或多 persona。
- 台語 STT／TTS 的 provider、支援腔調、品質門檻、成本與資料 Region。
- 真人轉接的實際對象、channel、營業時間、SLA 與緊急事件責任。
- 多任務 MVP 要同時處理、排隊處理，或只保存後逐項確認。
- 語言能力是自述、認證、評價或人工審核；媒合權重如何治理。
- 點數是否值得納入 MVP；若納入，獎勵何種可驗證服務行為。
- AWS 的帳號、Region、服務、模型、權限、預算與公開 hosting。
