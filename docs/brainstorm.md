# brainstorm.md — 候選作品方向腦力激盪（10 個）

> 前提：兩人小組（資工＋統計）、Python 為主、無前端與 AWS 實戰經驗、每天可投入時間中低。
> 所有候選方向都已對齊官方資料集：`pms_form` 動態表單七表、`mms_order_record` 訂單狀態機、`sys_county/sys_district` 縣市區域檔、六大服務商主檔（清潔／寄件／餐廳訂位／商城購物／修繕服務／美食外送）。
> 評分準則權重提醒：技術可行 25%＋商業應用 25%＋切合度 20%＝70%，創意只佔 15%。**穩與切題優先於炫**。

## 候選 1：修繕小隊長 — 拍照報修 × 動態諮詢單 × 報價媒合

### 1. 題目名稱
修繕小隊長：一張照片，搞定居家報修

### 2. 一句話概念
使用者拍一張故障照片、講一句話，AI 判斷問題類型、追問細節、自動填好水電修繕諮詢單，媒合師傅並走「勘驗 → 報價 → 同意 → 完工」全流程。

### 3. 使用者情境
獨居租屋上班族小陳，晚上十點發現馬桶不通。他不知道該找哪種師傅、行情多少、會不會被坑。他拍一張照片丟給管家：「馬桶塞住了，水一直退不下去」。AI 判斷是「水電修繕—馬桶不通」，追問「掉入的是軟性物質還是硬物？」「地址？」「明天上午師傅方便到嗎？」，產生諮詢單。師傅後台看到附照片與 AI 摘要的案件，一鍵接案回覆勘驗時間。

### 4. 核心流程
使用者輸入文字＋照片 → AI（多模態）判斷 service_type=水電修繕、sub_type=馬桶 → 追問缺漏欄位（依 `pms_form_topic` 題目清單）→ 產生諮詢單寫入 `pms_form_feedback` → 媒合邏輯依地區（sys_district）＋子類型＋評分推薦師傅 → 廠商後台看到案件＋AI 摘要 → 建立勘驗訂單（`mms_order_record`，order_status 11→12→13→14→80 報價狀態機）→ 使用者端看到狀態更新與通知。

### 5. 可 Demo 功能
1. 對話＋照片上傳 → AI 判斷故障類型（image understanding）
2. 多輪追問補齊諮詢單必填欄位（slot filling）
3. 諮詢單寫入 DB（沿用官方 `pms_form_feedback` schema，含 PII 加密欄位）
4. 廠商後台：案件列表＋AI 需求摘要＋接案按鈕
5. 訂單狀態機展示：待訂金 → 已付訂金待報價 → 已報價 → 同意報價（官方定義的 11–15 狀態）
6. MCP tool：`create_consultation_case`、`search_vendor` 被 agent 呼叫的過程可視化

### 6. AI 技術亮點
- image understanding（Claude 多模態直接判圖，不用自己訓模型）
- intent classification ＋ slot filling ＋ multi-turn dialogue
- function calling / MCP tool calling（判型 → 取表單 → 填單 → 媒合）
- summarization（給廠商的案件摘要）
- synthetic data generation（師傅、案例、評分資料）

### 7. AWS / 工具可能用法
- Amazon Bedrock（Claude 多模態＋tool use）
- S3（照片上傳，對應官方 feedback 裡的 upload-imgs 路徑格式）
- Lambda ＋ API Gateway（媒合 API）或容器直跑 FastAPI
- RDS PostgreSQL 或本機 Postgres（官方 schema 就是 PostgreSQL）
- CloudWatch（呼叫紀錄）、Kiro（開發過程加分）

### 8. 商業價值
修繕是高單價、低頻但高信任門檻的服務，正是統一「把便利店信任延伸到居家服務」的核心場景。官方訂單 schema 中專為服務訂單設計的報價狀態機（11–15）證明這是統一資訊真實在做的業務；範例資料裡 15 筆水電修繕訂單全是「現場勘驗費 $286」，代表勘驗→報價是真實流程。作品直接展示「AI 降低留資摩擦 → 提高諮詢單轉換率」。

### 9. 主題切合度
- 智慧零售：勘驗費、訂金、OpenPoint 點數欄位全部對上官方 schema
- AI 生活管家：住｜家事修繕直球場景
- 諮詢單／訂單／媒合：三者全走到，且用官方表結構
- 統一生態系：修繕完成可回推「到 7-ELEVEN 取修繕零件包」等延伸敘事

### 10. SWOT
| | |
|---|---|
| **S** | 與官方資料集重合度最高（馬桶子選項、勘驗費訂單都在範例裡）；照片判斷 demo 有記憶點；流程閉環完整 |
| **W** | 創意度中等（官方已想過這場景）；多模態判斷準確率需要 prompt 調校 |
| **O** | 可延伸「維修知識 RAG」「報價合理性提示」做出差異化 |
| **T** | 其他隊也可能選此場景；照片判斷失敗時 demo 尷尬（需準備測過的照片） |

### 11. 黑客松可行性評分
| 創意 | 技術可行 | 商業 | 切合 | 完成度 | 兩人可行 | AWS 展示 | Demo 觀賞 |
|---|---|---|---|---|---|---|---|
| 3.5 | 5 | 4.5 | 5 | 4.5 | 4.5 | 4 | 4.5 |

### 12. 風險
- 照片判斷不穩 → 一定要用預先測試過的照片庫 demo
- 報價狀態機做太細會吃掉時間 → 後台只做狀態按鈕切換即可
- 太像官方預設答案 → 需要在「AI 追問品質」與「摘要品質」上做出亮點

### 13. MVP 建議
**只做**：文字＋照片輸入 → 判型 → 追問 2–3 輪 → 諮詢單入庫 → 廠商後台列表＋摘要＋接案 → 狀態更新通知。
**砍掉**：真實報價計算、師傅端 App、地圖顯示、金流、評價系統（用假資料呈現即可）。

## 候選 2：LifeHub 社區生活媒合中樞 — 彈性諮詢單平台（命題直球）

### 1. 題目名稱
LifeHub：聽得懂需求的社區生活服務媒合中樞

### 2. 一句話概念
一個對話入口吃下清潔、修繕、訂位、外送、購物等多種生活需求，AI 判斷類型後動態產生該類型的諮詢單並媒合服務商，廠商後台統一管理案件。

### 3. 使用者情境
雙薪家庭的媽媽阿芳，週間晚上想一次處理三件事：週六請人打掃、冷氣該洗了、週日家庭聚餐訂位。她不想開三個 App 填三張表單。她對管家說一句話，管家逐項確認細節，產生兩張諮詢單＋一張訂位單，隔天清潔公司與餐廳分別在後台接案回覆。

### 4. 核心流程
使用者輸入 → AI 分類到六大服務類型（對齊官方主檔 type 1/2/3/6/9/10/11）→ 依類型從 `pms_form`/`pms_form_topic` 取出該表單題目 → AI 把對話內容對映到題目答案、追問缺漏必填題 → 組出 `feedback_content` JSON 寫入 `pms_form_feedback` → 媒合引擎依類型＋地區＋時段＋評分排序廠商 → 廠商後台接案、更新狀態 → 使用者端追蹤。

### 5. 可 Demo 功能
1. 同一入口 demo 兩種服務（如清潔＋訂位）證明「彈性」
2. 動態表單渲染：DB 裡的題目定義即時變成 UI 表單（官方 10 種題型做 4–5 種）
3. AI 對話自動預填表單、缺的才問（slot filling 可視化：欄位逐一亮起）
4. 媒合結果排序＋推薦理由
5. 廠商後台：案件列表、AI 摘要、已讀／狀態管理（對齊 `is_read`、`status` 欄位）
6. MCP Server：`classify_service_type` → `get_form_schema` → `create_consultation_case` 工具鏈

### 6. AI 技術亮點
- intent classification（六類服務）
- dynamic form generation（LLM 對映對話 → 官方表單 schema）
- multi-turn dialogue ＋ slot filling
- tool calling / MCP server（完整工具鏈）
- summarization（廠商端案件摘要）
- recommendation（媒合排序）

### 7. AWS / 工具可能用法
- Bedrock（Claude tool use）、S3（照片題）、RDS PostgreSQL／本機 Postgres
- Lambda＋API Gateway 包媒合 API（或 FastAPI 容器）
- Amplify／CloudFront 放前端（若前端獨立）
- CloudWatch＋Kiro

### 8. 商業價值
這就是統一資訊正在建的平台本體：把「表單留資」升級成「對話留資」，直接打擊留資表單棄填率——每降低一成棄填就是一成的商機轉換。多服務共用一套表單引擎＝新服務商上架零開發成本，符合統一「生活服務生態系」的平台策略，並可與 OpenPoint／UniOpen 會員體系串接。

### 9. 主題切合度
命題原文「餐廳推薦、購物推薦及社區服務諮詢單媒合平台」的直接實作，三個設計內容（彈性諮詢單、廠商後台、媒合邏輯）全部命中。切合度是十個候選中最高的。

### 10. SWOT
| | |
|---|---|
| **S** | 零審題風險；官方資料利用率最高；表單引擎通用性讓「彈性」有實據 |
| **W** | 創意分數天花板較低；容易做成「什麼都有但都淺」 |
| **O** | 用「動態表單引擎＋AI 預填」當技術主打，多數隊伍只會寫死表單 |
| **T** | 同題撞題率最高；評審看多了同型作品會疲乏，需要一個記憶點場景 |

### 11. 黑客松可行性評分
| 創意 | 技術可行 | 商業 | 切合 | 完成度 | 兩人可行 | AWS 展示 | Demo 觀賞 |
|---|---|---|---|---|---|---|---|
| 3 | 5 | 4 | 5 | 4.5 | 4.5 | 4 | 4 |

### 12. 風險
- 「多服務」誘惑導致每個都做一半 → 嚴格限制 demo 兩種服務
- 沒有記憶點 → 建議疊一個深度場景（見候選 1）或語音模組（見候選 3）
- 表單引擎過度工程 → 只支援官方 10 題型中的 4–5 種即可

### 13. MVP 建議
**只做**：兩種服務類型（建議清潔＋修繕，或清潔＋訂位）、動態表單 4 種題型（單選、複選、地區選單、簡答）、諮詢單入庫、媒合排序、廠商後台。
**砍掉**：全部六類服務、照片題以外的媒體題、審核流程（`review_status` 直接設已審核）、B 端表單編輯器。

## 候選 3：銀髮安心管家 — 語音優先 × 子女遠端代管

### 1. 題目名稱
銀髮安心管家：爸媽開口說，子女遠端看

### 2. 一句話概念
高齡者用語音說需求，AI 用大字體、慢節奏、一次一問的方式完成諮詢單；子女在遠端收到通知、可代為確認，服務進度雙端同步。

### 3. 使用者情境
70 歲的王伯伯獨居台南，電風扇壞了、也想找人打掃，但不會用 App 填表單。他對著平板說「電風扇不會轉了」。管家用語音回問「是完全不動，還是轉得很慢？」並用大按鈕讓他點選。諮詢單完成後，在台北上班的女兒收到 LINE 風格通知，確認預算後案件送出。師傅到府當天，女兒遠端看到「服務中 → 已完成」。

### 4. 核心流程
語音輸入 → STT 轉文字 → AI 判斷服務類型 → 高齡友善多輪追問（一次一題、選項化、TTS 唸出）→ 諮詢單暫存 → 通知家人帳號確認 → 寫入 `pms_form_feedback` → 媒合廠商 → 雙端狀態追蹤。

### 5. 可 Demo 功能
1. 語音輸入 → 即時轉文字 → AI 回應（可加 TTS 唸回）
2. 高齡友善 UI：大字、大按鈕、一次一問（同一套表單 schema、不同渲染模式——技術亮點）
3. 家人代管視角：第二個瀏覽器分頁演「女兒收到通知並確認」
4. 諮詢單入庫＋廠商後台接案
5. 「常用需求」記憶：AI 記得上次找過的清潔頻率（agent memory）

### 6. AI 技術亮點
- speech-to-text / text-to-speech（Transcribe＋Polly 或瀏覽器 Web Speech API 保底）
- 高齡友善 prompt 設計（口語化、一次一問、確認式對話）——差異化亮點
- multi-turn dialogue、slot filling
- agent memory（偏好與歷史）
- summarization（給子女的「爸媽需求摘要」）

### 7. AWS / 工具可能用法
- Amazon Transcribe（中文 STT）＋ Amazon Polly（中文 TTS）——AWS 語音服務展示點
- Bedrock、S3、RDS／Postgres、CloudWatch、Kiro
- 保底方案：瀏覽器 Web Speech API（不依賴 AWS 也能 demo）

### 8. 商業價值
台灣 2025 年進入超高齡社會，銀髮經濟是統一集團明確的策略方向（藥局、宅配、社區服務）。「子女付費、父母使用」是可說服評審的付費模型；命題文件明文鼓勵「探索高齡友善的對話互動設計」，說明會也點名長者用藥、跌倒、找不到師傅的情境。

### 9. 主題切合度
命題延伸應用第②點直接點名高齡友善；語音互動呼應統一「智慧管家可透過語音互動」的產品定位；諮詢單／媒合／後台流程不變，只是加上語音層與代管層。

### 10. SWOT
| | |
|---|---|
| **S** | 情感故事最強、demo 最有观赏性；社會價值好講；語音是現場少數隊伍敢做的 |
| **W** | 語音在現場網路／麥克風環境下是最大不穩因素；兩人做雙端 UI 工作量偏高 |
| **O** | Transcribe＋Polly 是很好的 AWS 架構圖素材；「同一表單雙渲染」是架構亮點 |
| **T** | 現場 demo 語音失敗風險；評審可能追問無障礙設計深度 |

### 11. 黑客松可行性評分
| 創意 | 技術可行 | 商業 | 切合 | 完成度 | 兩人可行 | AWS 展示 | Demo 觀賞 |
|---|---|---|---|---|---|---|---|
| 4 | 3.5 | 4 | 4.5 | 3.5 | 3.5 | 4.5 | 5 |

### 12. 風險
- 現場收音差 → 必備「預錄語音檔」與文字輸入 fallback
- 雙端（長者端＋子女端）UI 工作量 → 子女端可以只做通知＋一顆確認按鈕
- 只做語音殼、媒合空心 → 底層仍要有諮詢單與後台

### 13. MVP 建議
**只做**：語音輸入（Web Speech API 保底＋Transcribe 展示）、一次一問對話、單一服務場景（修繕或清潔）、子女確認通知（同機雙分頁模擬）、廠商後台簡版。
**砍掉**：TTS 全程語音導航、真 LINE 串接、多語言、跌倒偵測等 IoT 想像。
**最佳用法**：不單獨成題，作為候選 1 或 2 的「加分模組」。

## 候選 4：聚餐總管 — 餐廳推薦 × 訂位諮詢單

### 1. 題目名稱
聚餐總管：一句話搞定選餐廳到訂位

### 2. 一句話概念
使用者描述聚餐情境（人數、預算、氛圍、忌口），AI 推薦餐廳、比較選項、產生訂位單，模擬餐廳端確認流程。

### 3. 使用者情境
上班族要辦部門聚餐：12 人、人均 800、要包廂、兩位吃素、週五晚上。他不想在三個平台間切換比較。管家追問細節後給三家推薦＋推薦理由，選定後產生訂位需求單，餐廳後台確認桌位回覆。

### 4. 核心流程
輸入聚餐需求 → AI 抽取條件（人數／預算／區域／菜系／飲食限制）→ 查詢自建餐廳資料庫（RAG 或結構化查詢）→ 推薦排序＋理由 → 產生訂位單（`mms_order_record` order_type=02 訂位狀態機：待確認→已確認）→ 餐廳後台確認 → 通知使用者。

### 5. 可 Demo 功能
1. 條件抽取可視化（對話中逐步收集到的條件面板）
2. 推薦三家＋AI 生成推薦理由（含忌口過濾展示）
3. 訂位單建立與餐廳端確認（狀態 02→03）
4. 「訂不到第一志願自動遞補第二志願」的 agent 邏輯
5. 合成餐廳資料庫（50 家假餐廳，含菜系／區域／評分／包廂）

### 6. AI 技術亮點
- 結構化條件抽取（NER-like slot filling）
- recommendation ＋ 推薦理由生成
- RAG（餐廳資料檢索）或 SQL tool calling
- multi-turn 澄清（「兩位吃素是全素還是蛋奶素？」）

### 7. AWS / 工具可能用法
- Bedrock（含 embedding 模型做餐廳向量檢索，或直接 SQL 查詢）
- RDS／Postgres、Lambda 包 `recommend_restaurant` API、S3、Kiro

### 8. 商業價值
餐飲是統一集團主業之一（星巴克、Mister Donut、21 風味館…），訂位資料是高價值會員行為資料；說明會中官方親自示範了這個場景的問法（必比登、預算、氛圍），代表企業關心。

### 9. 主題切合度
「食」場景直球，餐廳推薦是命題明列的三大建置服務之一；訂位走官方訂位狀態機。但「社區服務」與「廠商媒合」色彩較弱，切合度略低於候選 1、2。

### 10. SWOT
| | |
|---|---|
| **S** | 技術簡單穩定、資料好生成、demo 流暢；推薦理由容易讓評審有感 |
| **W** | 與現有訂位平台（inline 類）差異化難講；媒合後台戲份少 |
