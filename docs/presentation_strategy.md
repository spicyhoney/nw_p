# presentation_strategy.md — 提案簡報策略

> **歷史規劃文件**：本頁包含 Demo 與簡報構想，不等於目前成果。任何「已完成」
> 宣稱與數字都必須重新對照[實作索引](implementation-index.md)、
> [資料品質報告](../reports/data_quality.md)及 [TASKS](../TASKS.md)。

> 評分：創意 15%｜技術可行 25%｜商業應用 25%｜切合度 20%｜完成度 15%｜Kiro +5%。
> 核心戰略：**用官方資料 schema 與可運行的閉環拿下技術+商業+切合的 70%**；創意用場景與敘事補，不用技術冒險換。
> （下文以「修繕＋清潔雙場景的生活管家媒合平台」為預設主體，換題目時結構不變。）

## 2. Demo 故事線（5 分鐘黃金劇本）

- **角色**：小陳，30 歲租屋上班族（主講人旁白扮演）；配角：師傅「安心水電坊」老闆（第二視窗）
- **痛點鋪陳（20 秒）**：晚上十點馬桶不通。Google 出來 20 家不知選誰，打電話沒人接，表單要填 15 格。
- **第一幕：對話輸入（60 秒）**——輸入「台北市大安區水龍頭漏水」，展示模型依序查詢服務、行政區與修繕表單；不宣稱照片或多模態。
- **第二幕：人工核對（60 秒)**——表單出現後，使用者親自完成 Checklist 與缺漏欄位。說明「模型只能建議，不能冒充使用者確認」。
- **第三幕：媒合（40 秒）**——推薦 2 家 synthetic 師傅並顯示地區、時段、評分、勘查費與可解釋理由；確認卡出現但尚未建案。
- **第四幕：廠商後台（60 秒）**——消費者明確確認後切到廠商頁：pending 只見遮罩 contact，廠商確認接案後才揭露完整 synthetic contact，消費者同步看到 `SYN-ORDER-*`。**閉環完成**。
- **第五幕：MCP 收束（40 秒）**——展示四個唯讀 Tool 與 protocol tests，說明 Streamable HTTP endpoint 已可啟動；只有完成 MCP-001 後才能改成外部 Agent 實際調用畫面。
- **高齡說明（時間許可 +20 秒）**：展示鍵盤操作、44px 觸控目標、明顯 focus 與手機響應式；語音仍是待辦。
- **保險**：每一幕都有預錄片段可切；DB/Inspector 畫面用預先開好的分頁。

## 3. 評審 Q&A 預演（18 題）

| # | 問題 | 回答方向 |
|---|---|---|
| 1 | 和一般 chatbot 差在哪？ | Chatbot 給答案，我們產生**結構化商業單據**：對話終點是符合官方 schema 的諮詢單＋媒合＋廠商工作流；LLM 全程只能走 tool 白名單，輸出可驗證可入庫 |
| 2 | 為什麼有商業價值？ | 把自由文字轉成結構化表單，降低消費者與廠商反覆確認的成本；目前沒有可信資料可量化提升幅度，因此不捏造轉換率或退款率 |
| 3 | 真的能落地嗎？ | Service／MCP／Repository 契約、雙端 workflow 與 PostgreSQL 已驗證；正式身分、真實個資、排程與 AWS 仍需完成，所以落地不是只剩商務簽約 |
| 4 | AWS 用在哪？ | 目前沒有 AWS 整合。目標是 Bedrock 做模型、AgentCore 託管 Agent／Gateway、RDS 保存資料、IAM 控制權限、CloudWatch 收集 log；圖中全部以虛線標成未完成 |
| 5 | MCP 用在哪？為什麼不用 REST 就好？ | REST 是網頁入口，MCP 是 Agent 的標準工具協定。四個 Tool 的 protocol tests 已通過；外部 HTTP Client 實測仍是 MCP-001，完成前不宣稱零客製接入 |
| 6 | 資料哪來的？ | 官方資料集包含 99 筆範例訂單、表單與縣市檔；B+ pipeline 將問題資料隔離。Demo 廠商、時段、案件與聯絡資料均標示 synthetic |
| 7 | 如何保護個資？ | 目前只使用 synthetic contact，pending 遮罩且 accepted 才揭露。官方 schema 的 AES-256-GCM＋hash 是正式環境要求，但本專案尚未實作真實 PII 加密與 KMS |
| 8 | 如何避免 hallucination？ | ①模型不能執行任意 SQL；②四個唯讀 Tool 有 schema 與白名單；③人工 Checklist 與派單確認不可由模型代勾；④固定 HF eval 仍在 TASKS，不能宣稱已完成 |
| 9 | 如何擴到統一生態系？ | Service、表單與 repository 邊界可重用，但新服務仍需可信主檔、專屬表單、媒合規則與測試，不宣稱零開發 |
| 10 | 廠商資料是假的，媒合有意義嗎？ | 媒合規則（地區／服務／評分／時段）可解釋且已有測試；換成真廠商資料後仍需資料品質、授權、排程與成效驗證，我們目前驗證的是機制而不是名單 |
| 11 | 官方不給 API 你們怎麼辦的？ | 依命題資料自行設計 FastAPI 與四個標準唯讀 MCP Tool；商業規則集中在 Service Layer。外部 Agent 若需要寫入，再新增有確認、身分、冪等與 audit 的受限 Tool |
| 12 | 為什麼選修繕/清潔場景？ | 官方資料訊號最強（範例含馬桶子選項、勘驗費訂單、報價狀態機）＋高信任門檻場景最需要 AI 降摩擦 |
| 13 | 語音準確率不高怎麼辦？ | 語音尚未實作。若投入，轉寫必須先回顯並由使用者確認，再進入既有文字與 Checklist 流程 |
| 14 | 兩人怎麼分工的？ | 依實際 commit 與 review 紀錄說明，不把尚未完成的 AWS、加密或 eval 分配冒充成果 |
| 15 | 最困難的技術點？ | 誠實選一個真的卡過的（如 tool use 參數穩定性/slot filling 不重複追問），講「問題→嘗試→解法→數據」 |
| 16 | 為什麼不用 LangChain/Bedrock Agents Classic？ | 目前只有四個唯讀 Tool，自寫迴圈較透明可測；AgentCore 是取得 AWS 環境後的目標 adapter，尚未託管 |
| 17 | Kiro 怎麼用的？ | 目前團隊決定不投入，repo 沒有可驗證 Kiro 紀錄，因此不申請或宣稱此加分 |
| 18 | 這個增長到十萬用戶會怎樣？ | 目前 Demo 尚未做容量證明。正式版需依壓測結果設計 API 水平擴展、RDS 容量／連線池、排程鎖、模型配額、快取與監控，不能把目標架構當成已驗證效能 |

> 演練方式：7/30 兩人互考，每題回答 ≤45 秒；答不出的題目回頭補一頁 appendix。
