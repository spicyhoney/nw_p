# presentation_strategy.md — 提案簡報策略

> 評分：創意 15%｜技術可行 25%｜商業應用 25%｜切合度 20%｜完成度 15%｜Kiro +5%。
> 核心戰略：**用官方資料 schema 與可運行的閉環拿下技術+商業+切合的 70%**；創意用場景與敘事補，不用技術冒險換。
> （下文以「修繕＋清潔雙場景的生活管家媒合平台」為預設主體，換題目時結構不變。）

---

## 2. Demo 故事線（5 分鐘黃金劇本）

- **角色**：小陳，30 歲租屋上班族（主講人旁白扮演）；配角：師傅「安心水電坊」老闆（第二視窗）
- **痛點鋪陳（20 秒）**：晚上十點馬桶不通。Google 出來 20 家不知選誰，打電話沒人接，表單要填 15 格。
- **第一幕：對話輸入（60 秒）**——輸入「馬桶塞住了，水退不下去」＋上傳照片。側欄即時顯示：`分類：水電修繕—馬桶（92%）`，表單欄位面板出現，照片判斷自動填入「馬桶堵塞／中等嚴重度」兩格（**亮點一：多模態預填**）。
- **第二幕：AI 追問（60 秒)**——AI 只問缺的：「住哪個行政區？」「明天上午方便嗎？」欄位隨回答逐一亮綠（**亮點二：slot filling 可視化**）。送出前彈出確認卡（講一句「AI 不擅自送單，人做最後確認」）。
- **第三幕：媒合（40 秒）**——單號產生；推薦 2 家師傅附理由「大同區可服務／馬桶疏通專長／評分 4.8」（**亮點三：可解釋媒合**)。順手秀 DB 一眼：姓名電話是密文＋hash（**亮點四：官方 schema 加密實作**，10 秒帶過）。
- **第四幕：廠商後台（60 秒）**——切視窗：案件列表→AI 摘要卡「10 秒讀懂：馬桶堵塞、大同區、明早、附 1 照」→按接案→切回消費者端：通知「王師傅已接案，明日 10:00 勘驗」→訂單狀態走到「已付訂金待報價」（官方狀態機字樣）。**閉環完成**。
- **第五幕：MCP 收束（40 秒）**——切 Inspector/外部 Agent 畫面：另一個 AI 管家調用 `search_vendor` 拿到同樣結果。收束句：「我們不只做了一個 App——我們把社區服務包成了任何智慧管家都能調用的標準工具。」（帶到 AWS 架構圖一眼）
- **彩蛋（時間許可 +30 秒）**：切高齡模式，播一段預錄語音「我想找人打掃」→大字介面一次一問。
- **保險**：每一幕都有預錄片段可切；DB/Inspector 畫面用預先開好的分頁。

## 3. 評審 Q&A 預演（18 題）

| # | 問題 | 回答方向 |
|---|---|---|
| 1 | 和一般 chatbot 差在哪？ | Chatbot 給答案，我們產生**結構化商業單據**：對話終點是符合官方 schema 的諮詢單＋媒合＋廠商工作流；LLM 全程只能走 tool 白名單，輸出可驗證可入庫 |
| 2 | 為什麼有商業價值？ | 留資轉換是服務電商第一瓶頸；引官方資料：範例訂單退款率 26%，需求釐清前置可降錯配；媒合抽成＋點數生態雙模式 |
| 3 | 真的能落地嗎？ | 資料層 100% 官方 schema、PII 加密照官方規格、MCP 對接 Lumine one——落地缺的是商務簽約不是技術重寫 |
| 4 | AWS 用在哪？ | 逐格指架構圖：Bedrock（理解/判圖/摘要）、S3（照片）、Lambda+APIGW（媒合 API）、CloudWatch（審計）；並誠實說明容器部分與「production 改 RDS/KMS」的演進 |
| 5 | MCP 用在哪？為什麼不用 REST 就好？ | REST 給人寫的前端呼叫，MCP 給 Agent 的標準接口：工具自描述、任何 MCP 客戶端零客製接入——現場 Inspector 調用就是證明 |
| 6 | 資料哪來的？ | 官方資料集（221 筆訂單、表單結構、縣市檔）＋合成資料（LLM 生成廠商與語料，人工審核、無真實品牌）；明確區分兩者 |
| 7 | 如何保護個資？ | 官方規格 AES-256-GCM 密文＋SHA-256 hash 查詢欄位（已實作，DB 可看）；LLM 只見遮罩；production 上 KMS 輪替 |
| 8 | 如何避免 hallucination？ | ①LLM 不直寫 DB，只能呼叫帶 schema 驗證的 tool；②送單前人工確認閘門；③低信心即反問不硬猜；④20+ 條 eval 迴歸測試，安全題全過 |
| 9 | 如何擴到統一生態系？ | 訂單表 points 欄位現成：服務完成發 OpenPoint 回流零售；新服務商上架＝在表單引擎建一張表單，零開發 |
| 10 | 廠商資料是假的，媒合有意義嗎？ | 媒合邏輯（地區/專長/評分/時段計分）是真的且可解釋；資料換成真廠商主檔即用——我們驗證的是機制不是名單 |
| 11 | 官方不給 API 你們怎麼辦的？ | 照命題精神自行假設 API 與格式：定義了 8 個 tool 的 I/O schema（openapi 亦附在 repo），未來真 API 進來只換 adapter 層 |
| 12 | 為什麼選修繕/清潔場景？ | 官方資料訊號最強（範例含馬桶子選項、勘驗費訂單、報價狀態機）＋高信任門檻場景最需要 AI 降摩擦 |
| 13 | 語音準確率不高怎麼辦？ | 雙通道設計，語音轉寫後回顯確認再進流程；轉寫錯誤由確認步驟攔截 |
| 14 | 兩人怎麼分工的？ | 資工：Agent/API/MCP/AWS/加密；統計：prompt 與 eval、合成資料、媒合計分、後台與統計圖表——各自對應未來職涯，講得出每行程式歸屬 |
| 15 | 最困難的技術點？ | 誠實選一個真的卡過的（如 tool use 參數穩定性/slot filling 不重複追問），講「問題→嘗試→解法→數據」 |
| 16 | 為什麼不用 LangChain/Bedrock Agents？ | 工具數 8 個、流程可控，自寫迴圈透明可測；託管編排在此規模是黑盒負債——規模化後才是它們的場景（未來頁有寫） |
| 17 | Kiro 怎麼用的？ | 指 repo `.kiro/` spec 與 commit 紀錄：用於生成後台頁/測試/README，核心 agent 邏輯自寫——按官方 log 認定方式呈現 |
| 18 | 這個增長到十萬用戶會怎樣？ | 無狀態 API 水平擴展、媒合已 serverless 化、DB 換 RDS 讀寫分離、Bedrock 配額提升——架構圖右側「production 演進」就是答案 |

> 演練方式：7/30 兩人互考，每題回答 ≤45 秒；答不出的題目回頭補一頁 appendix。
