# prototype_test_plan.md — 賽前 PoC / 測試計畫（20 項）

> 原則：每個測試都要在「大做之前」回答一個具體的風險問題。測試失敗不是壞事——賽前失敗的成本是 1 小時，賽場失敗的成本是名次。
> 標記：⏱ 預估時間（單人）；負責建議：A=資工、B=統計、AB=兩人。

---

## 第一梯隊：核心命脈（賽前必完成 Top 5）

### T01. Bedrock 第一次呼叫 ⭐
- **目的**：驗證帳號、IAM、Region 與指定模型全鏈路通
- **工具**：AWS 帳號、boto3｜**負責**：AB（各自跑通一次）｜⏱ 2h
- **成功標準**：`converse()` 回傳模型回覆；量到延遲數字
- **失敗替代**：主辦方尚未提供憑證或模型不可用 → 先用 Mock Model 開發，保留
  `ModelClient` 介面，Bedrock 可用後再切 adapter
- **影響**：不通則整個 AWS 故事重寫——**第一天就做**

### T02. Tool use 迴圈 ⭐
- **目的**：驗證 Claude 能穩定要求呼叫工具、參數格式正確、回填後能總結
- **工具**：boto3 toolConfig｜**負責**：A｜⏱ 3h
- **成功標準**：「我家馬桶不通」→ 依序觸發 classify→search 兩個 tool，參數 JSON 可直接 parse，10 次跑 9 次穩
- **失敗替代**：換 prompt 寫法（tool description 加範例）；仍不穩則改「LLM 只輸出 JSON、程式主導流程」的保守模式
- **影響**：Agent 架構的成立前提

### T03. 意圖分類準確率 ⭐
- **目的**：六類服務＋other 的分類 prompt 是否夠準
- **工具**：eval_cases.json（20 句，先手寫）＋跑分腳本｜**負責**：B｜⏱ 3h
- **成功標準**：≥18/20；易混對（家電清洗 vs 修繕）不錯
- **失敗替代**：加 few-shot 範例；仍差則縮減 demo 場景數
- **影響**：決定 demo 敢開放評審隨意輸入，還是只走劇本

### T04. 官方 SQL 匯入＋諮詢單寫入 ⭐
- **目的**：官方 schema 真的能撐起我們的流程
- **工具**：Docker Postgres、psql、psycopg｜**負責**：A（B 跟看）｜⏱ 3h
- **成功標準**：3 個 SQL 檔匯入零錯誤；照官方範例結構組一筆 feedback_content 寫入、讀回、JOIN 區域表成功
- **失敗替代**：DDL 有相依問題就調順序；最壞降級 SQLite（jsonb→TEXT）
- **影響**：資料層地基；也直接產出「我們用官方 schema」的簡報素材

### T05. MCP Server 最小版 ⭐
- **目的**：命題必做項的技術路線驗證
- **工具**：`pip install mcp`、MCP Inspector（npx）｜**負責**：A｜⏱ 3h
- **成功標準**：一個 `search_vendor` tool 被 Inspector 成功調用回傳 JSON；截圖/錄影存證
- **失敗替代**：Python SDK 卡住 → 抄官方 reference servers 的最簡 Python 範例改；再不行用 TypeScript 範例照抄（邏輯仍在 Python API 裡，MCP 層只做轉發）
- **影響**：交付硬需求，早通早安心

## 第二梯隊：功能風險排除（7/18 工作坊前後完成）

### T06. Slot filling 品質
- **目的**：對話→表單欄位對映＋追問生成是否自然
- **工具**：Bedrock＋修繕表單 schema｜**負責**：B｜⏱ 4h
- **成功標準**：3 段模擬對話都能正確標出已填/缺漏、追問一次只問一件事、不重複問已答資訊
- **失敗替代**：把「抽取」與「生成追問」拆成兩次 LLM 呼叫
- **影響**：作品核心體驗的品質上限

### T07. 多輪對話狀態管理
- **目的**：session 狀態（已收集答案）跨輪保存、換頁不丟
- **工具**：FastAPI＋chat_sessions 表（或先用記憶體 dict）｜**負責**：A｜⏱ 2h
- **成功標準**：關掉重開瀏覽器分頁，對話與已填欄位還在
- **失敗替代**：demo 版全放 server 記憶體＋單 session
- **影響**：demo 中斷重來的保險

### T08. 照片判斷（多模態）
- **目的**：Claude 看報修照片的準確度與穩定性
- **工具**：Bedrock 多模態＋自拍/網路授權圖 10 張（馬桶/水管/冷氣/電扇）｜**負責**：B｜⏱ 3h
- **成功標準**：10 張中 ≥8 張 problem_type 正確；輸出 JSON 格式 100% 可 parse
- **失敗替代**：demo 只用測過的 3 張黃金照片；問題照片改由使用者選單自報
- **影響**：demo 記憶點的可靠性

### T09. 動態表單渲染
- **目的**：DB 題目定義→Streamlit UI 的渲染引擎可行性
- **工具**：Streamlit（selectbox/multiselect/text_input/file_uploader/date_input）｜**負責**：B｜⏱ 3h
- **成功標準**：官方 10 題型中的 5 種（單選/複選/簡答/地區/照片）從 pms_form_topic 讀出即渲染
- **失敗替代**：放棄通用引擎，為 2 個 demo 表單寫死 UI（外觀相同，評審看不出）
- **影響**：「彈性諮詢單」的技術說服力

### T10. 媒合計分引擎
- **目的**：規則計分＋推薦理由的輸出品質
- **工具**：純 Python＋25 家假廠商｜**負責**：B（公式）＋A（API 化）｜⏱ 3h
- **成功標準**：給定（區、型、時段）回前 3 名＋每家 2 條理由；換區換型結果合理變化
- **失敗替代**：無（純邏輯必能完成，只有好壞之分）
- **影響**：「媒合平台」三個字的實質內容

### T11. 假資料生成管線
- **目的**：LLM 批量生成廠商/對話語料的品質與效率
- **工具**：Bedrock/Claude＋入庫腳本｜**負責**：B｜⏱ 3h
- **成功標準**：一次生成 25 家廠商 JSON 全部通過 schema 驗證入庫；名稱無真實品牌
- **失敗替代**：LLM 生 5 家人工複製變體
- **影響**：demo 質感與統計圖表的原料

### T12. PII 加密＋hash
- **目的**：AES-256-GCM＋SHA-256 兩函式與 DB bytea 欄位相容
- **工具**：Python cryptography｜**負責**：A｜⏱ 2h
- **成功標準**：加密入庫→hash 反查→解密顯示→後台遮罩，四步全通
- **失敗替代**：無技術風險；時間不足則只做 name/mobile 兩欄
- **影響**：官方 schema 對齊度＋資安 Q&A 底氣

### T13. 廠商後台頁
- **目的**：Streamlit 做案件列表＋詳情＋狀態按鈕的可行性
- **工具**：Streamlit multipage｜**負責**：B｜⏱ 3h
- **成功標準**：列表（st.dataframe）→點開詳情→按「接案」→DB 狀態改變→消費者頁下次刷新看到通知
- **失敗替代**：列表與詳情合一頁；通知改手動刷新
- **影響**：三端閉環的後半段

### T14. Docker Compose 全套啟動
- **目的**：一鍵起 postgres＋api＋ui，為未知部署環境做準備
- **工具**：Docker Desktop｜**負責**：A｜⏱ 2h
- **成功標準**：`docker compose up` 後瀏覽器可用；換一台電腦重現成功
- **失敗替代**：UI 不進容器（本機跑），只容器化 db＋api
- **影響**：EDIMUS/Ademus 應變能力＋隊友環境一致

### T15. Lambda＋API Gateway 打通
- **目的**：AWS 增量架構的第一塊
- **工具**：AWS console｜**負責**：A｜⏱ 3h
- **成功標準**：公網 curl `POST /vendors/search` 回排序結果；CloudWatch 看得到 log
- **失敗替代**：架構圖照畫、註明「等效服務以 FastAPI 承載」，demo 不受影響
- **影響**：AWS 展示分的增量

- **失敗替代**：手動 SQL（風險高不建議）
- **影響**：排練效率與現場救場能力
