# 提案與繳交準備總計畫

更新日期：2026-08-01

本計畫不採倒數排程，而是依「必要交付、依賴關係、驗收關卡」安排。每一項都要有可交付成果與完成定義，避免只有口頭說明。

## 1. 交付範圍與目前狀態

### 1.1 提案必須涵蓋的內容

1. 提案與命題的連結。
2. 企業數據及資料應用。
3. AWS 雲端技術架構。
4. 生成式 AI 技術應用。
5. Live Demo。
6. 遵守競賽規範、命題資料集與企業工作坊公告。
7. 團隊自行延伸的亮點。

### 1.2 入口頁需要繳交的項目

1. 團隊基本資料。
2. 提案大綱。
3. 完整提案簡報電子檔。
4. Live Demo 部署網址。
5. Live Demo 錄製影片連結。
6. GitHub 連結，且包含完整原始碼。

### 1.3 官方命題文件補充要求

- 主題是「AI 生活管家：智慧社區服務需求理解與媒合平台」。
- 核心情境包含消費者彈性留資表單、服務廠商後台、案件與媒合流程。
- 參賽團隊需自行設計 API，並包裝成標準 MCP Server，供外部 Agent 調用。
- 評分權重：創意 15%、技術可行性 25%、商業應用性 25%、主題切合度 20%、完成度 15%。
- Kiro 為 +5% 加分項，只有在有真實開發證據時才主張。

## 2. 統一提案主線

### 2.1 一句話版本

讓使用者用自然語言描述居家修繕需求，由 AI 生活管家建立符合官方資料結構的彈性諮詢單，透過受控 MCP 工具媒合服務商，再讓廠商於後台承接與更新案件。

### 2.2 Demo 應證明的閉環

```text
使用者描述需求
  -> AI 判斷服務類型並補問必要欄位
  -> 形成彈性諮詢單與確認清單
  -> MCP 工具依服務、地區等條件查詢候選廠商
  -> 使用者確認送出
  -> 廠商後台看到案件並承接
  -> 案件狀態與稽核紀錄可查
```

### 2.3 提案敘事原則

- 先講痛點與使用者結果，再講模型與架構。
- 每個技術方塊都必須對應一個畫面、測試或程式證據。
- 已完成元件使用實線；目標架構與未完成 AWS 元件使用虛線。
- 不宣稱已完成 Bedrock、AgentCore、RDS、正式登入、真實個資處理或 Kiro 加分，除非完成並留下證據。
- 展示資料一律標示為官方範例衍生或 synthetic，不冒充真實消費者或廠商資料。

### 4.2 資料頁必講清楚的四件事

1. 使用了哪些官方檔案與表格。
2. 清理了哪些問題，以及哪些資料被隔離或採 synthetic 替代。
3. 哪些欄位實際驅動表單、媒合、案件狀態與廠商後台。
4. 如何避免個資、密鑰與真實聯絡資訊進入 GitHub 或 Demo。

## 5. 提案簡報建議結構

沿用既有 `docs/presentation_strategy.md`，收斂為以下 10 頁：

1. **封面與一句話價值**：題目名稱、團隊、目標使用者。
2. **命題痛點與切題性**：銀髮族/忙碌家庭的需求，以及與 AI 生活管家的直接連結。
3. **解法與使用者流程**：自然語言 -> 彈性表單 -> 媒合 -> 廠商承接。
4. **Live Demo**：切換至實機，頁面只留備援截圖與 Demo 網址。
5. **企業資料應用**：官方資料血緣、欄位對照與品質檢查。
6. **生成式 AI 與 MCP**：模型只負責理解/決策，受控工具負責查詢，Service Layer 執行規則。
7. **目前架構與 AWS 目標架構**：實線/虛線清楚區分，說明 Bedrock、AgentCore、RDS、IAM、CloudWatch。
8. **商業價值與可落地性**：對消費者、服務商與統一資訊各自的價值與可衡量指標。
9. **安全、資料治理與風險控制**：synthetic、PII、秘密管理、稽核與 fallback。
10. **完成度、差異化與下一步**：已完成、仍待完成、GitHub/影片/Live Demo QR code。

每頁至少有一個證據：操作畫面、架構圖、資料表、測試結果或 Repo 路徑；避免整頁只有願景文字。

## 6. Live Demo 與錄影劇本

### 6.1 黃金路徑

1. 從消費者首頁輸入明確但不完整的修繕需求。
2. 展示 AI 補問、服務分類與彈性表單/確認清單。
3. 展示 MCP 查詢候選服務商，並說明模型不直接寫 SQL。
4. 使用者確認送出，產生案件或 Demo 訂單編號。
5. 切到廠商後台，看到 pending 案件並承接。
6. 回到消費者端確認狀態更新；若適合，再補一個工具 trace 或稽核證據。

### 6.2 備援層級

- A：公開 Live Demo 正常，完整操作。
- B：Live Demo 仍可開啟但模型 provider 異常，切換固定 Mock 案例並明確說明。
- C：部署故障，播放已錄好的同版 Demo 影片與備援截圖。
- D：網路故障，使用本機啟動流程，但繳交網址仍需事前驗證可公開使用。

### 6.3 影片內容

- 開頭：問題與一句話解法。
- 主體：完整黃金路徑，消費者端與廠商端都要出現。
- 技術證據：短暫帶到資料來源、MCP/tool trace 與實際使用的模型/provider。
- 結尾：商業價值、Live Demo 與 GitHub。
- 影片長度、格式與平台權限依現場/入口頁公告，不自行假設。

## 7. AWS 與生成式 AI 決策閘門

### 情況 A：AWS 權限完整

1. 先驗證身分、Region、模型 ID、額度與一次 Converse 呼叫。
2. 實作 `BedrockModelClient`，沿用既有 Agent/MCP/Service 契約，不重寫核心流程。
3. 用固定案例驗證 tool selection、參數抽取、失敗處理與延遲。
4. 若環境仍穩定，再考慮 RDS、AgentCore 或 CloudWatch；每加入一項都要有實際證據。

### 情況 B：AWS 權限不完整或不穩定

1. 以現有 Mock/Hugging Face 與本機 PostgreSQL 路徑確保 Demo 閉環。
2. AWS 圖只畫「目標架構」，全部以虛線和未完成標記呈現。
3. 提案清楚說明 adapter 邊界與遷移方式，不宣稱已部署。
4. 將技術可行性證據放在 MCP、Service Layer、資料契約、測試與可替換 provider。

## 8. GitHub 交付整理

### README 首屏需要回答

- 這是什麼問題、給誰使用、解法是什麼。
- 一張目前架構圖，以及一張目標 AWS 架構圖或同圖的實線/虛線版本。
- Live Demo 與影片連結。
- 最短啟動方式、必要環境變數與 fallback 模式。
- 主要功能、資料來源、MCP 工具與測試方式。
- 目前限制；不得把未完成 AWS 元件寫成已完成。

### Repo 驗收

- `git status` 只留下預期變更。
- `.env.example` 只有欄位名與安全範例，不含真實秘密。
- 執行秘密資料掃描、`git diff --check` 與完整測試。
- 從乾淨目錄 clone 後依 README 啟動一次。
- 確認 default branch、可見性、授權與所有必要檔案均可讀。
- 建立明確的 submission tag 或 release，讓繳交版本可追溯。

## 10. 風險與處理方式

| 風險 | 早期訊號 | 處理方式 |
|---|---|---|
| 公開部署不穩 | 冷啟動、逾時、外部無法連線 | 健康檢查、固定 Demo seed、影片與本機備援 |
| 真實模型不穩或額度不足 | provider error、延遲過高 | 固定案例、timeout、明確 fallback 至 Mock，不隱瞞模式 |
| AWS 尚無權限 | 無法確認帳號/Region/model | 保留目標架構，將技術證據集中在可測契約與 MCP |
| 簡報誤稱未完成功能 | 架構圖與 Repo 不一致 | 實線/虛線審查，逐頁指定證據負責人 |
| 資料或個資外洩 | Repo 出現 `.env`、真實電話地址 | synthetic 資料、secret scan、外部審查 |
| GitHub 無法重現 | 新環境啟動失敗 | 乾淨 clone 驗證、固定依賴、更新 README |
| 影片或連結無權限 | 登入狀態下可看、無痕不可看 | 使用無痕視窗與第二裝置逐一驗證 |
| 入口規格仍有變動 | 現場公告與舊 PDF 不同 | 以 8/1 現場/入口公告為最高優先，更新 Gate 1 |
